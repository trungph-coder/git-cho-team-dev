Mục tiêu: sau 60 phút, mỗi dev tự tin với vòng làm việc hằng ngày, viết commit và đặt tên nhánh theo quy ước chung, và tự xử lý các sự cố hay gặp (conflict, commit nhầm, mất commit). Hỏi nhanh khán giả: ai từng xoá repo clone lại vì Git "hỏng"? Đó là lý do buổi này bắt đầu từ mô hình tư duy.

Lộ trình: 5 chặng, mỗi chặng xây trên chặng trước

Lộ trình vẽ như một nhánh Git: mỗi chặng là một commit. Bấm để từng chặng hiện ra. Chặng 1 là nền: hiểu Git lưu gì thì các lệnh ở chặng 2 và cách cứu ở chặng 4 trở nên dễ đoán thay vì phải học thuộc. Chặng 3 là quy ước team, chặng 5 là những điều không thể hoàn tác.
01

Mô hình tư duy

Hiểu Git lưu gì, thì mọi lệnh đều dễ đoán.

Phần này ít lệnh. Mục tiêu là có một bức tranh đúng trong đầu: commit, staging, branch, remote. Hầu hết sự hoảng loạn với Git đến từ việc không biết mình đang đứng ở đâu trong bức tranh này.

Commit là ảnh chụp, không phải bản vá

Snapshot toàn bộ project, kèm tác giả, thời gian, message và commit cha

Hash tính từ nội dung: nội dung đổi một ký tự, hash đổi hoàn toàn

Nên không sửa được commit: "sửa" là tạo commit mới. Gốc của mọi cảnh báo về viết lại lịch sử

Phân tán: mỗi máy có đủ lịch sử, commit và xem log không cần mạng

commit 9f8e7d6
tree4b825dc (snapshot) parenta1b2c3d authorAn <an@team.dev> date2026-10-23 09:14 messagefeat(cart): add coupon

hash = SHA-1( tree + parent + author + message )

Bấm từng ý. Ở ý 2, nhìn sang thẻ bên phải: chỉ thêm một chữ "s" vào message, hash đổi hoàn toàn. Vì hash tính từ nội dung, commit không bao giờ bị sửa: "sửa" thực chất là tạo commit mới với hash mới. Đây là gốc của mọi cảnh báo về viết lại lịch sử ở phần sau. Git phân tán: mỗi máy có toàn bộ lịch sử, nên commit, xem log, tạo nhánh đều chạy offline.

Một thay đổi đi qua bốn vùng

Bước 1

Sửa file

Thay đổi chỉ nằm ở working directory. Git chưa lưu gì cả.

Bước 2 · git add

Đưa vào staging

Bản nháp của commit kế tiếp. Chọn từng đoạn bằng git add -p.

Bước 3 · git commit

Chốt thành snapshot

Có hash, nằm trong .git ở máy bạn. Lỡ tay vẫn cứu được. Chưa ai thấy.

Bước 4 · git push

Lên remote

Đồng đội fetch được. Từ đây đừng viết lại lịch sử nữa.

Chiều ngược lại

Lệnh nào cũng có đường về

Khi bối rối: git status luôn nói thay đổi đang ở vùng nào.

$git status
Changes not staged for commit:
modified: login.ts
Changes to be committed:
modified: login.ts
Your branch is ahead of 'origin/main'
by 1 commit.
nothing to commit, working tree clean
Your branch is up to date with
'origin/main'.

Theo dõi chip login.ts bay qua từng vùng, và terminal bên phải đổi theo. Bước 1: sửa file, thay đổi chỉ ở working directory, git status hiện màu đỏ. Bước 2: git add đưa vào staging, bản nháp commit kế tiếp; staging cho phép commit một phần. Bước 3: git commit chốt thành snapshot có hash; chip đổi thành hash. Bước 4: git push, đồng đội fetch được, từ đây viết lại lịch sử là nguy hiểm. Bước 5: các mũi tên ngược: restore, restore --staged, fetch/pull.

Branch chỉ là con trỏ tới một commit

$git status # On branch feat/login $git commit -m "feat(login): remember me" $git switch main $git switch --detach C

HEAD → feat/login → F

Branch là một file nhỏ ghi hash của commit mới nhất. HEAD cho biết bạn đang đứng ở đâu.

Commit mới, con trỏ nhích lên

G ra đời, feat/login và HEAD trượt sang G. main đứng yên. Tạo nhánh gần như miễn phí.

Chuyển nhánh = dời HEAD

Không có commit nào bị copy. Git chỉ đổi file trong thư mục cho khớp commit D.

Detached HEAD

HEAD trỏ thẳng vào commit. Commit ở đây dễ thất lạc; muốn giữ thì git switch -c <tên>.

Branch không chứa code; nó chỉ ghi hash commit mới nhất. Bấm lần 1: commit G, con trỏ feat/login và HEAD cùng trượt sang G, main đứng yên. Lần 2: git switch main chỉ dời HEAD. Lần 3: detached HEAD, HEAD trỏ thẳng vào commit C. Commit làm ở đây không có tên nào giữ, nên dễ thất lạc; muốn giữ thì tạo nhánh.

Gọi tên commit: HEAD~1, origin/main

$git show HEAD
commit D, nơi bạn đang đứng
$git show HEAD~1
commit C, cha của D
$git diff HEAD~3 HEAD
mọi thay đổi từ A tới D
$git log --oneline origin/main..main
C, D: hai commit bạn chưa push
$git reset --soft HEAD~1
"lùi con trỏ về C", giữ thay đổi

HEAD

Bạn đang đứng ở đâu

HEAD trỏ vào nhánh hiện tại, nhánh trỏ vào commit mới nhất: D.

~1 = lùi 1 bước

HEAD~1 là C

Dấu ~ đi ngược về commit cha. HEAD~1 = commit ngay trước HEAD.

~3 = lùi 3 bước

HEAD~3 là A

Đếm ngược ba lần theo cha. Dùng hash ngắn cũng được: git show a1b2c3d.

origin/main

Bản chụp server

origin là tên mặc định của remote. origin/main = main trên server ở lần fetch cuối, đang ở B.

Dùng ở đâu

Mọi lệnh nhận commit

reset, diff, show, log, rebase, cherry-pick đều nhận HEAD~n, tên nhánh hoặc hash.

Trước khi học reset hay rebase, cần biết cách gọi tên một commit. HEAD là nơi bạn đứng. Dấu ngã cộng số là lùi bao nhiêu bước theo commit cha: HEAD~1 là commit trước, HEAD~3 là ba bước trước. origin là tên mặc định Git đặt cho server khi bạn clone; origin/main là bản chụp nhánh main của server ở lần fetch cuối. origin/main..main nghĩa là "các commit có ở main mà origin/main chưa có", tức là chưa push.

Local và remote: fetch khác pull

Trước

Đồng đội vừa push C, D

Máy bạn chưa biết gì. origin/main là bản chụp remote ở lần fetch cuối.

git fetch

Tải về, không đụng code

C, D về máy, origin/main nhích lên. main của bạn đứng yên. Luôn an toàn.

git pull = fetch + merge

Cập nhật nhánh của bạn

main trượt lên D. Có thể sinh conflict. Nên đặt pull.rebase = true.

Lane trên là server, lane dưới là máy bạn. Lần bấm 1, git fetch: commit C, D bay từ server về máy, origin/main nhích lên D, nhưng main của bạn đứng yên ở B, code đang làm không bị đụng. Lần bấm 2, git pull: main trượt lên D. Thói quen tốt: fetch trước, xem có gì mới, rồi mới quyết định merge hay rebase.

Upstream: ahead và behind là gì

$git push -u origin HEAD
branch 'feat/login' set up to track 'origin/feat/login'.
$git branch -vv
* feat/login 9f8e7d6 [origin/feat/login: ahead 2, behind 1] feat(login): remember me
main a1b2c3d [origin/main] chore: bump deps

git push -u

-u gắn nhánh với một nhánh trên server

Từ đó git push, git pull, git status biết so với đâu. Nhánh trên server đó gọi là upstream.

Upstream

origin/feat/login

Nhánh của bạn đang theo dõi nhánh cùng tên trên server.

ahead 2

Bạn có 2 commit server chưa có

Cần git push.

behind 1

Server có 1 commit bạn chưa có

Thường do đồng đội push. Cần git pull --rebase trước, rồi mới push.

Đây là thông tin quan trọng nhất trong git status mà nhiều người bỏ qua. -u ở lần push đầu gắn nhánh local với nhánh trên server (upstream). Sau đó Git đếm: ahead là số commit bạn có mà server chưa có, behind là ngược lại. Cả ahead lẫn behind cùng lúc nghĩa là hai bên đã rẽ nhánh: pull --rebase rồi push.
02

Lệnh hằng ngày

Một vòng làm việc chuẩn, từ lúc nhận task đến lúc mở merge request.

Bộ lệnh dùng 95% thời gian. Không cần nhớ hết tuỳ chọn, chỉ cần nhớ vòng làm việc và câu hỏi mỗi lệnh trả lời.

Thiết lập một lần cho mỗi máy

$git config --global user.name "Nguyen Van An"
$git config --global user.email "an@company.com"
$git config --global init.defaultBranch main
$git config --global pull.rebase true
$git config --global fetch.prune true
$git config --global rerere.enabled true
$git config --global core.editor "code --wait"
$ssh-keygen -t ed25519 -C "an@company.com"

--global

Áp cho mọi repo trên máy

Lưu ở ~/.gitconfig. Bỏ --global thì chỉ áp cho repo hiện tại. Bấm để xem từng dòng làm gì.

user.name / user.email

Tên và email ghi vào mọi commit

Email phải trùng email tài khoản GitLab, nếu không commit hiện là người lạ, không có avatar.

init.defaultBranch

Repo mới tạo dùng nhánh main

Thay vì master, để khớp với GitLab và GitHub.

pull.rebase

git pull = fetch + rebase

Tránh commit rác kiểu Merge branch 'main' of gitlab… mỗi lần pull.

fetch.prune

Dọn nhánh đã xoá trên server

MR merge xong, nhánh trên server bị xoá thì origin/feat/… ở máy cũng biến mất.

rerere = reuse recorded resolution

Git nhớ cách bạn giải conflict

Gặp lại đúng conflict đó (hay xảy ra khi rebase nhiều lần), Git tự áp lại cách giải cũ.

core.editor

Editor mở khi viết message

Dùng cho git commit không có -m và rebase -i. --wait: chờ bạn đóng tab.

SSH key

Đăng nhập bằng khoá, bỏ mật khẩu

Dán nội dung ~/.ssh/id_ed25519.pub vào GitLab › Preferences › SSH Keys, rồi thử ssh -T git@gitlab.com.

Mỗi lần bấm sáng một dòng config và giải thích nó làm gì. --global lưu vào ~/.gitconfig, áp cho mọi repo. Quan trọng nhất là email đúng tài khoản và pull.rebase. rerere nghĩa là reuse recorded resolution: Git ghi nhớ cách bạn giải một conflict và tự áp lại khi gặp lại đúng conflict đó. SSH key: tạo cặp khoá, dán public key vào GitLab, kiểm tra bằng ssh -T.

Hunk là gì

Một đoạn thay đổi liền nhau trong file. Git hỏi lần lượt từng hunk.

PhímNghĩa
yĐưa đoạn này vào commit
nBỏ qua, vẫn giữ trong file
sTách thành đoạn nhỏ hơn
eSửa tay từng dòng
qThoát

Bắt được console.log debug. Kết quả: commit chỉ có dòng làm tròn, console.log vẫn ở file để bạn xoá.

add -p duyệt từng hunk, tức một đoạn thay đổi liền nhau. Bấm 1: đoạn này lẫn một dòng console.log debug. Bấm 2: gõ s để tách thành hai hunk nhỏ. Bấm 3: n cho console.log, y cho dòng làm tròn. Kết quả commit sạch. Đây là bước tự review rẻ nhất trong ngày.

Mới nhất ở trên

Đọc từ trên xuống

Mỗi dòng một commit, càng xuống càng cũ.

Một commit

Cột chứa dấu * cho biết commit nằm trên nhánh nào.

Hash ngắn

7 ký tự đầu của hash

Đủ để gọi tên commit: git show 3f2a9c1.

Ngoặc đơn

Các con trỏ đang ở đây

HEAD → main: bạn đang ở main. origin/main cùng chỗ: đã đồng bộ với server.

Nhánh tách ra, nhập lại

Lệnh này là bản đồ của repo. Bấm lần lượt: dấu sao là một commit; chuỗi vàng là hash ngắn; phần trong ngoặc là các con trỏ (HEAD, nhánh local, nhánh remote) đang trỏ vào commit đó; dấu gạch chéo là chỗ nhánh tách ra và nhập lại. Làm việc với nhánh

$git switch -c feat/GAV-123-login # tạo + chuyển
$git switch main # chuyển nhánh
$git switch - # về nhánh trước
$git branch -vv # nhánh + tracking
$git push -u origin HEAD # đẩy lần đầu
$git branch -d feat/GAV-123-login # xoá (đã merge)
$git fetch --prune # dọn nhánh remote đã xoá

switch / restore

Thay cho checkout: một lệnh, một việc, ít gõ nhầm hơn.

-d an toàn, -D ép

-d từ chối xoá nhánh chưa merge. Chỉ dùng -D khi chắc chắn.

git switch và git restore tách từ git checkout cũ (vốn làm quá nhiều việc). Khuyến khích team dùng switch/restore cho rõ nghĩa. Xoá nhánh bằng -d an toàn: Git từ chối nếu nhánh chưa merge. Nhánh remote đã merge nên xoá luôn; GitLab có tuỳ chọn tự xoá khi merge.

Merge hay rebase?

# main có thêm C, D trong lúc bạn làm E, F $git switch main && git merge feat/login # quay lại, lần này thử rebase $git switch feat/login && git rebase main $git switch main && git merge --ff-only feat/login
Cùng một điểm xuất phát, hai cách đưa thay đổi của main vào.
Merge: thêm commit M, giữ nguyên lịch sử. An toàn cho nhánh dùng chung.
Rebase: E, F được chép thành E′, F′ trên D. Hash mới.
Fast-forward: main chỉ trượt con trỏ lên, không cần commit gộp. Rebase nhánh của mình, merge vào nhánh chung.
Cùng một đồ thị, hai cách. Bấm 1: merge tạo commit M nối hai nhánh, không viết lại gì. Bấm 2: quay lại. Bấm 3: rebase gỡ E, F ra và áp lại lên đầu D thành E′, F′: nội dung giống nhưng cha khác nên hash khác, bản cũ mờ đi. Bấm 4: main chỉ việc trượt lên, lịch sử thẳng. Quy tắc vàng ở dải cuối.

Mẹo: --fixup

git commit --fixup 1111111 rồi git rebase -i --autosquash origin/main: Git tự xếp sẵn.

5 commit lộn xộn ở local (wip, fix typo) trở thành 2 commit sạch trước khi push. Bấm 1: đổi chữ đầu dòng, fixup gộp commit vào commit phía trên và bỏ message của nó; reword giữ commit nhưng cho sửa message. Bấm 2: kết quả còn hai commit. Chỉ làm trên nhánh của mình, vì đây là viết lại lịch sử. Bấm 3: mẹo --fixup và --autosquash.
03

Quy ước team

Lịch sử Git là tài liệu: viết sao cho người sau đọc được.

Quy ước giúp review nhanh hơn, revert chính xác hơn, bisect được, và sinh changelog tự động. Người đọc lịch sử nhiều nhất chính là bạn của sáu tháng sau.

Khi nào nên commit?

Nên

Một thay đổi logic, mô tả được bằng một câu

Mọi commit đều build và test pass

Commit thường ở local, dọn lại trước khi push

Tách refactor, đổi tên, format khỏi đổi hành vi

Tránh

Trộn nhiều task trong một commit

Mỗi lần bấm hiện một cặp nên/tránh. Một commit là một thay đổi logic hoàn chỉnh, mô tả được bằng một câu và revert độc lập. Ở local, commit thường như điểm lưu game; trước khi push thì dọn lại bằng rebase -i. Mọi commit trên nhánh chung nên build được, để git bisect hoạt động.

Semantic versioning

Ba con số, ba ý nghĩa

Nhìn số là biết bản mới có an toàn để nâng cấp không.

fix → PATCH

1.4.0 → 1.4.1

Chỉ sửa lỗi. Nâng cấp yên tâm.

feat → MINOR

1.4.1 → 1.5.0

Thêm tính năng, không phá gì. PATCH về 0.

feat! → MAJOR

1.5.0 → 2.0.0

Phá vỡ tương thích. Người dùng phải đọc hướng dẫn nâng cấp.

$git tag -a v1.5.0 -m "Release 1.5.0"
$git push origin v1.5.0
$git tag --list "v1.*"
# tag = con trỏ đứng yên, branch = con trỏ di chuyển
Tag là con trỏ giống branch nhưng không bao giờ di chuyển: đánh dấu đúng commit đã phát hành. Semver: MAJOR.MINOR.PATCH. Bấm từng bước để thấy fix, feat và breaking change đẩy số nào lên. Đây là lý do commit message cần đúng type: công cụ release đọc type để tính version.

Ngôn ngữ trong review

LGTM

"Looks good to me": đồng ý, có thể merge.

nit:

Góp ý nhỏ, không bắt buộc sửa.

Request changes

Phải sửa rồi mới merge. Trả lời từng thread, resolve khi xong.

Một mô tả MR tốt trả lời bốn câu: cái gì, vì sao, test thế nào, trông ra sao. Đặt mẫu này vào .gitlab/merge_request_templates để GitLab tự điền. Bên phải là vài từ hay gặp trong review: LGTM là đồng ý, nit là góp ý nhỏ không bắt buộc.

Ba cách merge một MR

Nhánh có 3 commit F1, F2, F3. Main đã có thêm C.
Merge commit: giữ đủ 3 commit và thêm M. Lịch sử đầy đủ nhưng rối.
Squash: 3 commit gộp thành 1 commit S trên main. Gọn, revert cả tính năng bằng một lệnh.
Rebase + fast-forward: chép từng commit lên main, lịch sử thẳng. Hợp khi mỗi commit đã sạch.
GitLab cho chọn cách merge trong cài đặt project. Merge commit giữ mọi thứ. Squash gộp cả MR thành một commit: phù hợp đa số team vì một MR là một tính năng, revert một lệnh là xong. Rebase rồi fast-forward giữ từng commit nhưng thẳng hàng: chỉ đáng khi mọi người viết commit sạch. Fast-forward nghĩa là main chỉ việc trượt con trỏ lên, không cần tạo commit gộp.

Tình huống thực tế

"Tôi đang gặp chuyện X. Tôi gõ gì?"

Mỗi slide là một tình huống có thật, kèm lệnh xử lý và điều cần cẩn thận. Câu hỏi đầu tiên ở mọi tình huống: thay đổi này đã push lên nhánh người khác dùng chưa?

Lỡ tay ở commit cuối

# quên add src/forgot.ts vào commit C
$git add src/forgot.ts
$git commit --amend --no-edit
C được thay bằng C′ (hash mới)

Chưa push

Amend thoải mái: thêm file quên, sửa message bằng --amend -m "…".

Đã push, nhánh riêng

git push --force-with-lease. Không dùng --force trần.

Đã push, nhánh chung

Đừng amend. Tạo commit mới sửa lỗi.

Bấm một lần: amend thay C bằng C′ với hash mới; C cũ mờ đi vì không còn tên nào trỏ vào. Nếu chưa push thì thoải mái. Đã push lên nhánh riêng thì cần push --force-with-lease. Đã push lên nhánh chung thì đừng amend: tạo commit mới sửa lỗi.

Đang dở việc, phải chuyển nhánh gấp

A

git stash

Gián đoạn vài phút. pop = lấy ra và xoá khỏi danh sách, apply = lấy ra nhưng giữ lại.

$git stash push -u -m "wip"
$git switch hotfix/GAV-9
# ...sửa, commit...
$git switch -
$git stash pop
B

git worktree

Gián đoạn dài: thư mục thứ hai, nhánh khác, dùng chung lịch sử.

$git worktree add \
../app-hotfix main
$cd ../app-hotfix
# thư mục thứ hai, chung .git
$git worktree remove ../app-hotfix
C

Commit WIP

Trên nhánh của riêng mình

$git commit -am "wip"
$git switch hotfix/GAV-9
# ...quay lại sau...
$git switch -
$git reset --soft HEAD~1
Chọn theo độ dài gián đoạn. Stash cho vài phút; nhớ -u để cất cả file mới. Worktree cho gián đoạn dài hoặc cần chạy song song hai nhánh: thư mục thứ hai dùng chung .git, không phải clone lại. Commit WIP rồi reset --soft sau cũng hoàn toàn hợp lệ trên nhánh riêng.

Bỏ thay đổi chưa commit

LệnhTôi muốn…
git restore <file>Bỏ sửa một file (chưa add)
git restore --staged <file>Bỏ khỏi staging, giữ nội dung đã sửa
git restore .Bỏ mọi thay đổi trên file đã track
git restore --source main <file>Lấy file về như ở main
git clean -ndXem trước file rác chưa track sẽ bị xoá
git clean -fdXoá thật file chưa track
Thay đổi chưa commit không có undo. Nhìn git status trước khi bỏ.
restore là lệnh chuyên để bỏ thay đổi. Bấm để hiện cảnh báo: thay đổi chưa từng commit thì không vào reflog, xoá là mất thật. Vì vậy luôn status và diff trước. git clean luôn chạy -n (dry run) trước.

Hoàn tác commit: reset hay revert?

# commit C chưa push $git reset --soft HEAD~1 $git reset HEAD~1 # --mixed, mặc định $git reset --hard HEAD~1 $git revert C # C đã push lên main
Câu hỏi quyết định: commit đã push lên nhánh chung chưa?
--soft: bỏ commit, thay đổi nằm sẵn ở staging. Hay dùng để commit lại.
--mixed: bỏ commit, thay đổi về working dir, chưa staged.
--hard: bỏ cả thay đổi. C vẫn còn trong reflog để cứu.
Đã push lên nhánh chung → luôn git revert: thêm commit đảo ngược.
Theo dõi con trỏ main và chip "thay đổi của C". --soft: main lùi về B, thay đổi nằm ở staging. --mixed: thay đổi về working dir. --hard: thay đổi biến mất, nhưng C vẫn còn trong reflog. Nếu C đã push lên nhánh chung: revert thêm commit đảo ngược, không viết lại lịch sử của ai.

Giải conflict từng bước

1

2

Đọc cả hai phía, hiểu ý định từng bên

3

Sửa thành bản đúng, xoá dấu conflict

4

Build + chạy test lại

5

git add rồi git rebase --continue

Rối quá? git rebase --abort về như cũ.
// src/config.ts

=======

>>>>>>> feat/GAV-88-config

$git add src/config.ts && git rebase --continue
Conflict không phải lỗi: Git chỉ nói hai người sửa cùng chỗ, nó không đoán được ý bạn. Bấm 2: đọc cả hai phía. Bấm 3: dấu conflict biến mất, bản đúng thường kết hợp cả hai ý, ở đây là cấu hình được nhưng giữ mặc định 30s của main. Sau đó build, test, add, continue. Rối thì abort, không mất gì.

Trong conflict, phía nào là của mình?

Đang làmPhía trên (HEAD, ours)Phía dưới (theirs)

Lấy nguyên một phía cho cả file

$git checkout --ours src/config.ts
$git checkout --theirs src/config.ts

Trong VS Code

Accept Current = phía trên, Accept Incoming = phía dưới, Accept Both = giữ cả hai. Khi rebase, hai chữ này đảo nghĩa như bảng trên.

Đây là chỗ gây nhầm nhiều nhất. Khi merge, phía trên là nhánh bạn đang đứng. Khi rebase thì ngược lại: phía trên là main, phía dưới mới là commit của bạn, vì rebase đứng trên main rồi áp lại từng commit của bạn. Nên khi rebase mà bấm Accept Current trong VS Code là đang chọn bản của main, không phải của bạn.

Commit nhầm vào main

# quên tạo nhánh: X, Y nằm trên main (chưa push) $git branch feat/GAV-123-x # giữ X, Y $git reset --hard origin/main # main về như remote $git switch feat/GAV-123-x

Branch chỉ là con trỏ, nên sửa rất rẻ. Commit nhầm vào nhánh khác đã có: git cherry-pick <sha> sang nhánh đúng.

Quên tạo nhánh, commit thẳng X, Y vào main local. Bấm 1: tạo nhánh mới tại Y để giữ commit. Bấm 2: kéo con trỏ main về origin/main; X, Y giờ chỉ còn thuộc nhánh mới. Bấm 3: chuyển sang nhánh đó làm tiếp. Nhớ git fetch trước để origin/main là bản mới nhất.

Nhánh bị tụt sau main: --force-with-lease

Tình huống

Bạn vừa rebase xong

Trong lúc đó đồng đội đẩy T lên cùng nhánh. Máy bạn chưa fetch nên không biết.

git push --force

Ghi đè mù

Server bị thay bằng bản của bạn. Commit T của đồng đội mất khỏi nhánh.

git push --force-with-lease

Từ chối, T an toàn

Chỉ ghi đè nếu server vẫn đúng như lần fetch cuối. Fetch, rebase lại, rồi push.

Lane trên là server, lane dưới là máy bạn sau khi rebase. Đồng đội vừa đẩy T. Bấm 1: --force ghi đè mù, T biến mất khỏi nhánh trên server. Bấm 2: --force-with-lease thấy server khác với lần fetch cuối nên từ chối; T an toàn. Quy trình đúng: git fetch, git rebase origin/main, chạy test, git push --force-with-lease.

cherry-pick: chép một commit sang nhánh khác

# bug đã sửa ở main (commit H), bản 1.4 đang chạy production cũng cần
$git switch release/1.4
$git cherry-pick -x 7c8d9e0
[release/1.4 b4c5d6e] fix(cart): round total

-x thêm dòng (cherry picked from commit 7c8d9e0) vào message, để sau này biết H′ đến từ đâu.

Tình huống điển hình: bug đã được sửa ở main, nhưng bản 1.4 đang chạy production cũng cần bản vá. cherry-pick chép đúng thay đổi của commit H thành commit mới H′ trên nhánh release. Hash khác vì cha khác. Đừng dùng cherry-pick để chuyển cả loạt commit giữa các nhánh thường xuyên: đó là dấu hiệu quy trình nhánh có vấn đề.

1

Commit nào đã thêm hoặc xoá một đoạn code.

An toàn & sự cố

Những lỗi không hoàn tác được, và cách để không bao giờ gặp.

Phần lớn lỗi Git sửa được nhờ reflog. Phần này nói về số ít lỗi không sửa được: ghi đè lịch sử người khác, và lộ secret.

Năm điều không bao giờ làm

1

push --force lên main / nhánh chung

Dùng --force-with-lease, chỉ trên nhánh của mình

2

Commit secret: .env, API key, token

.gitignore, biến môi trường, secret scanning

3

Rebase/amend commit người khác đã pull

Lịch sử của họ lệch, sinh commit trùng lặp

.gitignore ở gốc repo cho thứ project sinh ra; .gitignore global cho rác của máy bạn. File binary lớn dùng Git LFS, nếu không mỗi phiên bản nằm vĩnh viễn trong repo. .gitattributes chuẩn hoá xuống dòng để không có diff đổi toàn bộ file giữa Windows và macOS.

Lỡ commit rồi mới thêm vào .gitignore?

.gitignore chỉ áp cho file chưa được track. Phải gỡ khỏi Git:

$git rm --cached .env
$git commit -m "chore: untrack .env"
Vài quy tắc đủ dùng: dấu sao khớp mọi ký tự, gạch chéo ở đầu là chỉ ở gốc repo, gạch chéo ở cuối là chỉ thư mục, dấu chấm than là ngoại lệ. git check-ignore -v cho biết dòng nào đang bỏ qua một file. Lỗi hay gặp: thêm .env vào .gitignore sau khi đã commit nó; Git vẫn theo dõi cho tới khi git rm --cached. Và nếu đó là secret thì xem lại slide lộ secret.

Git LFS là gì

Large File Storage: repo chỉ giữ một file con trỏ vài dòng, file thật nằm ở kho riêng và chỉ tải khi cần.

design/banner.psd trong repo

version https://git-lfs.github.com/spec/v1
oid sha256:4d7a2146b3e0f6…
size 214958234
$git lfs install
$git lfs track "*.psd" "*.mp4"
$git add .gitattributes design/banner.psd

Sửa file 200 MB 10 lần

Không LFS2 GB

Mọi phiên bản nằm vĩnh viễn trong repo, ai clone cũng phải tải hết.

Có LFS200 MB

Clone chỉ tải đúng phiên bản đang dùng.

Git lưu mọi phiên bản của mọi file mãi mãi. Với code thì không sao, với file thiết kế hay video 200 MB thì repo phình rất nhanh. LFS thay file thật bằng một file con trỏ ba dòng như hình; file thật nằm ở kho LFS và chỉ được tải về đúng phiên bản bạn checkout. Cần bật LFS trước khi commit file lớn lần đầu.

pre-commit trả về 1

Git dừng ngay: không có commit, không có gì bị mất. Sửa rồi commit lại.

# .git/hooks/pre-commit (ví dụ tự viết)
#!/bin/sh
npx eslint --max-warnings=0 $(git diff --cached \
--name-only --diff-filter=ACM -- '*.ts')
# eslint lỗi → exit 1 → commit bị chặn
Hook là script Git tự chạy ở các thời điểm cố định. Bấm để đi qua một lần commit và push: pre-commit chạy trước khi commit được tạo, commit-msg chạy sau khi bạn viết message, pre-push chạy trước khi gửi lên server. Bước cuối: nếu script trả mã lỗi khác 0, Git dừng thao tác. Lưu ý: thư mục .git/hooks không được commit, nên team dùng husky, lefthook hoặc pre-commit để chia sẻ hook qua repo. Hai slide sau là ví dụ cụ thể.

Ví dụ: pre-commit chặn một commit

# .husky/pre-commit
npx lint-staged
// package.json
"lint-staged": {
"*.{ts,tsx}": ["eslint --fix",
"prettier --write"],
"*": "gitleaks protect --staged"
}

husky: cài hook từ repo cho cả team. lint-staged: chỉ chạy trên file đã stage, nên nhanh. gitleaks: quét secret.

$git commit -m "feat(cart): coupon"
✔ Preparing lint-staged...
✖ eslint --fix:
src/cart.ts 14:3 error 'sum' is never used
husky - pre-commit script failed (code 1)
# → không có commit nào được tạo. Sửa cart.ts…
$git commit -m "feat(cart): coupon"
✔ eslint --fix ✔ prettier --write ✔ gitleaks
[feat/GAV-123 9f8e7d6] feat(cart): coupon
Bên trái là cấu hình thật: husky chạy lint-staged mỗi lần commit; lint-staged chạy eslint và prettier trên các file ts đã stage, và gitleaks quét mọi file để bắt key bị lộ. Bên phải: lần commit đầu bị chặn vì biến không dùng. Bấm 1: không có commit nào được tạo. Bấm 2: sửa xong, commit lại, mọi bước qua.

Ví dụ: commit-msg và pre-push

# .husky/commit-msg
npx --no -- commitlint --edit "$1"
// commitlint.config.js
export default { extends: ["@commitlint/config-conventional"] }
$git commit -m "fix bug"
⧗ input: fix bug
✖ subject may not be empty [subject-empty]
✖ type may not be empty [type-empty]
$git commit -m "fix(cart): round total to 2 decimals"
[fix/GAV-207 2c3d4e5] fix(cart): round total to 2 decimals
# .husky/pre-push
bun run typecheck && bun test --bail
$git push
✖ cart.test.ts › applies two coupons
husky - pre-push script failed (code 1)
# → không có gì được gửi lên server

commitlint đọc message và so với quy tắc Conventional Commits. pre-push chặn đẩy code làm hỏng test.

commitlint chạy trong hook commit-msg: "fix bug" bị từ chối vì thiếu type theo chuẩn. Bấm 1: viết đúng chuẩn thì qua. Bấm 2: pre-push chạy type check và test trước khi gửi lên server; test hỏng thì không có gì được đẩy lên. Giữ pre-push nhanh (dưới khoảng 30 giây), phần nặng để CI chạy.

Để máy nhắc, thay vì dựa vào trí nhớ

Một commit đi qua năm cửa trước khi vào main.
Hook local chạy nhanh trên máy bạn: format, lint, kiểm message, test nhanh.
CI chạy đầy đủ trên MR; main được bảo vệ, không ai push thẳng.
--no-verify bỏ qua được hook local, nên CI mới là cổng bắt buộc.
Theo dõi commit đi qua từng cửa. Ba cửa đầu là hook local (husky, lefthook hoặc pre-commit): format, lint, quét secret, kiểm message, test nhanh. Cửa 4 là CI trên MR, cửa 5 là main được bảo vệ. Bấm cuối: ai đó dùng --no-verify nhảy qua hook local, nhưng vẫn bị CI chặn. Đó là lý do CI là cổng bắt buộc.

CI và nhánh được bảo vệ

CI (Continuous Integration): server tự chạy kiểm tra cho mọi MR, trên máy sạch, không ai bỏ qua được.

install→lint→typecheck→test→build→secret scan
# .gitlab-ci.yml (rút gọn)
stages: [check, test]
lint:
stage: check
script: bun run lint
test:
stage: test
script: bun test

Settings › Repository › Protected branches

main · Allowed to pushNo one
main · Allowed to mergeMaintainers
Pipelines must succeed
All threads must be resolved
CI là server tự chạy cùng bộ kiểm tra cho mọi MR trên một máy sạch: không phụ thuộc máy ai, không ai --no-verify được. Bấm để các stage lần lượt xanh. Bấm cuối: cài đặt nhánh được bảo vệ trên GitLab: không ai push thẳng vào main, chỉ merge qua MR, và chỉ merge được khi pipeline xanh và mọi thread review đã được giải quyết. Đây là thứ biến quy ước thành luật.
